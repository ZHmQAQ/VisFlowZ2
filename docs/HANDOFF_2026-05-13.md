## 1. 项目定位与验收口径

### 1.1 VModule 与 VisFlowZ 的关系

- `VisFlowZ` 是参考项目。
- `VModule` 是我们的目标项目。
- 两者**不要求 preset / 配置格式兼容**。
- 但 VModule 必须能够**完整覆盖 VisFlowZ 的同类业务流程**。

这一点很重要：后续任何“兼容性”讨论，都应该优先按“业务流程是否覆盖”来判断，而不是按字段名、JSON 结构、页面布局是否一模一样来判断。

### 1.2 当前验收口径

当前已经明确采用以下口径验证“是否还原了 VisFlowZ 业务逻辑”：

1. `VisFlowZ` 导出的参考配置能够被人工映射到 VModule。
2. 映射后的 VModule 配置能够被 VModule 自身导入。
3. 导入后的运行态可以通过 VModule 新增的业务自检。
4. 自检通过的标准是：**所有 required 项通过**；warning 项作为参考项记录。

当前这套口径已经落地到代码，不再只是口头约定。

## 5. 参考业务流程：VisFlowZ 这份配置到底在做什么

本节对应两个文件：

- 参考源：`D:\agentzone\visflowz-config-2026-05-13.json`
- VModule 映射结果：`D:\agentzone\VModule\visflowz-config-vmodule-2026-05-13.json`

### 5.1 业务主线概述

当前参考流程本质上是一个双工位检测流程：

- 工位 `pos2`：4 帧检测
- 工位 `pos3`：1 帧检测

PLC 给命令，VModule 根据命令触发采图与推理，再把 ACK、最终结果、计数和耗时回写给 PLC。

### 5.2 配置规模概览

`visflowz-config-vmodule-2026-05-13.json` 当前包含：

- 1 个 PLC 连接
- 8 条 I/O 映射
- 0 个单帧检测通道
- 2 个多帧检测通道
- 2 台相机
- 2 个外部设备
- 6 条事件动作
- 2 条规则

这说明当前映射不是“混着做一部分单帧、一部分多帧”，而是明确以**多帧通道模型**承载业务流程。

### 5.3 相机层

参考配置里有两台 Hikvision 相机：

#### `pos2`

- 类型：`hikvision`
- 序列号：`DA8290609`
- 触发模式：`software`
- 曝光：`30000`
- 多帧曝光列表：`[30000, 30000, 30000, 30000]`

#### `pos3`

- 类型：`hikvision`
- 序列号：`DA8290709`
- 触发模式：`software`
- 曝光：`40000`
- 多帧曝光列表：`[40000]`

### 5.4 PLC 与关键地址关系

VModule 自检当前要求的关键 I/O 映射是：

| 业务含义 | VModule 地址 | PLC 地址 |
|---|---|---|
| pos2 命令 | `ED60` | `D60` |
| pos2 响应 | `EW61` | `D61` |
| pos3 命令 | `ED62` | `D62` |
| pos3 响应 | `EW63` | `D63` |

除了上面这 4 组关键映射，配置里还存在统计类地址映射，总数一共是 8 条。

### 5.5 `pos2` 多帧业务

`pos2` 的多帧流程当前被建模为：

- 命令地址：`ED60`
- 状态地址：`EW61`
- 结果地址：`EW61`
- 缺陷数量地址：`EW0`
- 耗时地址：`EW1`

帧计划如下：

| 帧序号 | PLC 命令值 | ACK 回写码 | 曝光 |
|---|---:|---:|---:|
| 第 1 帧 | `1` | `17` | `30000` |
| 第 2 帧 | `2` | `18` | `30000` |
| 第 3 帧 | `3` | `19` | `30000` |
| 第 4 帧 | `4` | `20` | `30000` |

也就是说：

1. PLC 往 `D60/ED60` 写入命令值 `1~4`
2. VModule 执行对应采图与推理
3. 每完成一帧，就往 `EW61/D61` 回写对应 ACK
4. 最终再把汇总结果回写到同一响应地址

### 5.6 `pos3` 多帧业务

`pos3` 当前是单命令的多帧通道形式：

- 命令地址：`ED62`
- 状态地址：`EW63`
- 结果地址：`EW63`
- 缺陷数量地址：`EW10`
- 耗时地址：`EW11`

帧计划如下：

| 帧序号 | PLC 命令值 | ACK 回写码 | 曝光 |
|---|---:|---:|---:|
| 第 1 帧 | `1` | `17` | `40000` |

### 5.7 最终结果码策略

两个工位统一采用：

- OK：`7`
- 可返修 NG：`6`
- 致命 NG：`5`
- 异常 / 错误：`255`

### 5.8 缺陷优先级策略

当前自检要求的缺陷优先级顺序是：

1. `NG`
2. `HP_NG`
3. `QJ_NG`
4. `RJ_NG`
5. `LX_NG`

缺陷类别映射到结果码的逻辑是：

- `NG` -> `ng_fatal`
- `HP_NG` -> `ng_repairable`
- `QJ_NG` -> `ng_repairable`
- `RJ_NG` -> `ng_repairable`
- `LX_NG` -> `ng_repairable`

### 5.9 保存与复位策略

两个工位当前都采用：

#### 保存策略

- `mode = ng`
- `image_format = png`
- `save_json = true`

含义：主要保存 NG 图片，并带 JSON 信息。

#### 复位策略

- `mode = wait_plc_zero`
- `clear_status_on_zero = false`

含义：等待 PLC 侧归零/复位，不在 VModule 内部过早清掉状态。

### 5.10 事件动作层

当前共有 6 条事件动作，结构上是：

#### `pos2`

- `on_cam_ok` -> 写 ACK
- `on_cam_fail` -> 写错误码 `255`
- `on_cycle_done` -> 写最终结果码

#### `pos3`

- `on_cam_ok` -> 写 ACK
- `on_cam_fail` -> 写错误码 `255`
- `on_cycle_done` -> 写最终结果码

动作本质上是“事件驱动的 PLC 回写逻辑”，把“拍照成功 / 失败 / 周期结束”的内部事件翻译成 PLC 能识别的寄存器值。

### 5.11 规则层

当前有两条规则：

- `pos2 NG 保存图像并报警`
- `pos3 NG 保存图像并报警`

每条规则当前都包含两类动作：

1. 保存图像
2. 触发可视化报警

这代表 VModule 不是只完成了“PLC 通讯意义上的回写”，还把 NG 后处理动作也串上了。

### 10.2 `setuplite.bat` 当前逻辑

- 激活可用 Python 环境

- `setuplite.bat` 已支持复用 `envVisFlowZ / visf`
- `startlite.bat` 目前只显式检查：
  - `envVModule`
  - `vmodule`
  - `.venv`
  - `backend\.venv`

也就是说，如果机器上只有 `envVisFlowZ` 或 `visf`，而没有 `envVModule / vmodule / .venv`，那么：

- `setuplite.bat` 可能能复用成功
- 但 `startlite.bat` 不一定能自动沿用它

这个点**建议后续尽快修**，否则“setup 能过、start 不认环境”的体验会不一致。
