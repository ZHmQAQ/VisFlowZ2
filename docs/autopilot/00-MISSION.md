# Autopilot Mission — `feat/rule-engine-wizard`

## 北极星目标（North Star）

**做一个复杂性上限高、同时又用户友好的工业视觉检测 + 虚拟 PLC 软件。**

一句话理解：**下限做到让 PLC 工程师 15 分钟配通第一条产线；上限做到让高级用户能用规则引擎+虚拟寄存器组合出任意"事件 → 动作"的自动化流程**，而现有的"检测通道"等高层抽象只是规则引擎的**预置模板**，不是核心。

## 为什么要做

**现状问题（由项目 Owner 识别）**

1. VisFlowZ 留下"流水线/管道"思维遗产，导致"检测通道"被当成核心一等公民。
2. 虚拟寄存器 (SoftDeviceMemory) + 扫描引擎 (ScanEngine) 明明已经实现了，但**没被充分利用为"事件驱动"的基础**。
3. 规则引擎 (`rule.py`)、事件动作 (`event_action.py`) 是**附加的**，不是核心调度器。
4. 对 PLC 工程师来说，这违背了他们的"母语"：PLC 世界本质就是寄存器 + 扫描 + 规则。
5. 对新用户，14 项菜单扁平排列，没有引导；配置流程隐含在界面顺序中，只能问 AI 才能上手。

**目标状态**

1. 规则引擎成为一等公民，检测通道/多帧通道变成"自动生成的规则预设"。
2. 新用户走**向导**（Wizard），15 分钟配通第一条产线；不看规则引擎也能用。
3. 高级用户点"展开为规则"，看到底层规则；可自由编辑、组合、新建。
4. 两种抽象级别**共存**：简单模式（通道）与完整模式（规则）可以互相转换。
5. 底层只有一套引擎，不再有 DetectionBlock / MultiFrameBlock / RuleEngine / EventAction 四套并行机制。

## 约束与非目标

**约束**
- 现有部署不能炸（向后兼容现有预设 JSON 格式至少 1 个大版本）。
- 不破坏 `feat/visflowz-launch-2026-05-13` 分支上的现场功能。
- 性能：多帧场景不得比现状退化超过 20%。
- 不引入新的外部依赖（不加 Celery、不加 Redis、不加 Kafka）。保持单进程 FastAPI + SQLite。

**非目标**
- 不做"真正的 PLC 编译器"。梯形图只做可视化，不做代码生成。
- 不做分布式运行时。单机即可。
- 不做多租户。一台设备一个用户。
- 不重写 VisFlowZ 的相机/推理内核。这部分是稳定资产。

## 成功标准

**Phase 1 MVP 验收**（约 1 周）

一个**完全没接触过本系统**的工程师，拿到文档（或看向导），能在 **15 分钟内**完成：
1. 连接一台真实 PLC（或 Modbus 模拟器）
2. 打开一台相机
3. 绑定一个模型
4. 配置一条触发信号
5. 启动引擎
6. 手动模拟触发一次，看到检测结果回写到 PLC

且全过程**不需要跳出向导**。

**Phase 3 完整版验收**

一个熟练用户，能够用规则编辑器**不写代码**地实现：
1. "M100 上升沿 → 拍照 + 推理 + 结果写 D200"（等价于当前检测通道）
2. "D300 > 100 时，每 5 秒抓图存盘"（当前做不到）
3. "连续 3 次 NG → 发送 TCP 报警到外部设备"（当前要靠规则+事件动作两套凑）
4. "多帧累积：M100=1 拍一张，M100=2 拍另一张，凑齐后合成判定"（等价于当前多帧块）

且上述 4 种场景，配置完的规则集合能**互相嵌套、互相触发**。

## 给 agent 的精神内核

1. **不要为"完美"牺牲"可用"**。现场在跑。每一个 PR 都要能单独部署。
2. **不要贪多**。一次 PR 一个主题。
3. **遇到不确定，问**。在 `05-DECISIONS-LOG.md` 写下问题，停下等答复。不要自作主张大改。
4. **读代码再动手**。本项目核心模块有精细的语义（触发沿、重置信号、awaiting_reset），不读透就重构会踩雷。
5. **测试先行**（对规则引擎这种核心组件）。改一行业务逻辑前，先证明旧行为在新代码下仍然成立。
6. **尊重 PLC 工程师的母语**。界面术语、默认值、报错提示，都要符合工业控制语境。
